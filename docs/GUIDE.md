## 1. Что делает программа

Это консольная программа для магазина автозапчастей. В ней хранятся:

- **клиенты** — кто заказывает (ФИО, телефон, email, город);
- **заказы** — какую запчасть заказал клиент (название, артикул, марка авто, категория, количество, цена, статус).

Все данные лежат в базе PostgreSQL. Пользователь работает через текстовое меню: вводит номер пункта,
программа выполняет действие и снова показывает меню. Выход — пункт `0`.

Жизненный цикл заказа (статусы):

```
Новый ──► Подтверждён ──► Отправлен ──► Доставлен
  │            │
  └──► Отменён ◄┘
```

## 2. Минимум Java, чтобы читать код

### Класс и объект

**Класс** — это чертёж, **объект** — вещь, сделанная по чертежу.
`Customer` — класс «клиент»: описывает, какие у клиента есть данные и что с ним можно делать.
`new Customer("Иванов", "+7916...", "ivanov@mail.ru", "Москва")` — создаёт конкретного клиента (объект).

### Поля, методы, конструктор

```java
public class Customer {
    private String fullName;          // поле — данные объекта

    public Customer(String fullName) { // конструктор — вызывается при new, заполняет поля
        this.fullName = fullName;      // this.fullName — поле, fullName — параметр
    }

    public String getFullName() {      // метод — действие объекта
        return fullName;
    }
}
```

### Модификаторы доступа

| Слово | Значит |
|-------|--------|
| `private` | видно только внутри этого класса |
| `public` | видно всем |
| `protected` | видно в этом классе и в наследниках |
| `static` | принадлежит классу, а не объекту (вызывается как `TablePrinter.printOrders(...)`, без `new`) |
| `final` | значение нельзя изменить после присваивания |

### Типы данных, которые встречаются в проекте

| Тип | Что хранит | Пример |
|-----|-----------|--------|
| `int` | целое число | `quantity = 2` |
| `String` | текст | `"Масляный фильтр"` |
| `BigDecimal` | точное дробное число (для денег) | `new BigDecimal("690.00")` |
| `LocalDate` | дата | 15.01.2026 |
| `LocalDateTime` | дата и время | 02.07.2026 10:15 |
| `boolean` | да/нет | `true` / `false` |
| `List<Order>` | список заказов | `[заказ1, заказ2, ...]` |
| `Map<String, String>` | пары «ключ → значение» | `"Всего заказов" → "15"` |
| `Optional<Customer>` | «клиент или ничего» | результат поиска по ID |

Почему `BigDecimal`, а не `double`: `double` хранит числа приближённо, и `0.1 + 0.2` даёт `0.30000000000000004`.
Для денег это недопустимо.

### Пакеты и import

Файлы разложены по папкам-пакетам: `ru.mirea.autoparts.model`, `ru.mirea.autoparts.service` и т. д.
Строка `import ru.mirea.autoparts.model.Order;` в начале файла говорит: «я буду использовать класс Order из пакета model».

### Лямбда и ссылка на метод

Короткая запись функции «на месте»:

```java
order -> order.getStatus() == OrderStatus.NEW   // «для заказа order верни: статус равен NEW?»
Order::getCreatedAt                              // «возьми у заказа дату создания»
```

Используются в фильтрации и сортировке (раздел 9).

### switch со стрелками

```java
switch (choice) {
    case 1 -> create();
    case 2 -> showAll();
    default -> throw new IllegalStateException("...");
}
```

Если `choice == 1`, вызвать `create()` и так далее.

## 3. Архитектура: слои

Программа разделена на слои, и каждый занимается только своим делом:

```
Console UI  ──►  Service  ──►  Repository / JDBC  ──►  PostgreSQL
 (пакет ui)     (service)       (repository)            (база)
```

| Слой | Пакет | Что делает | Чего НЕ делает |
|------|-------|-----------|----------------|
| Console UI | `ui` | показывает меню, читает ввод, печатает результат | не пишет SQL, не проверяет бизнес-правила |
| Service | `service` | проверяет данные и бизнес-правила, фильтрует, сортирует, считает статистику | не знает про консоль и не пишет SQL |
| Repository | `repository` | выполняет SQL-запросы через JDBC, превращает строки таблицы в объекты | не проверяет бизнес-правила |
| Database | PostgreSQL | хранит данные, следит за ограничениями (ключи, UNIQUE, CHECK) | — |

Вспомогательные пакеты:

- `model` — классы данных (`Customer`, `Order`) и перечисления (`OrderStatus`, `PartCategory`); ими пользуются все слои;
- `exception` — наши исключения;
- `util` — подключение к базе и экспорт в файлы.

**Зачем слои?** Каждую часть можно понять и изменить отдельно. Например, если перейти с PostgreSQL на MySQL,
поменяется только `repository` и `db.properties`, а меню и бизнес-логика останутся прежними.

## 4. Путь одного действия через все слои

Разберём, что происходит, когда пользователь создаёт заказ: **2 → 1**.

1. **`Main.main`** при запуске создал все объекты и запустил `MainMenu.run()`.
2. **`BaseMenu.run`** (цикл меню) прочитал `2` и вызвал `MainMenu.handle(2)`, который запустил `orderMenu.run()`.
3. В подменю пользователь ввёл `1`, и был вызван **`OrderMenu.create()`**. Он через `ConsoleInput` спрашивает
   ID клиента, название, артикул, марку, категорию, количество и цену. `ConsoleInput` не даст ввести текст вместо числа.
4. `OrderMenu` вызывает **`orderService.create(...)`**:
   - `ensureCustomerExists` проверяет, что клиент с таким ID есть (иначе `EntityNotFoundException`);
   - `validate` проверяет, что поля не пустые, количество от 1 до 100, цена > 0 (иначе `BusinessException`);
   - создаёт объект `new Order(...)` со статусом «Новый».
5. `OrderService` вызывает **`orderRepository.save(order)`**:
   - открывает соединение `Connection`;
   - готовит `INSERT INTO orders (...) VALUES (?, ?, ...)` через `PreparedStatement`;
   - подставляет значения `setInt`, `setString`, `setBigDecimal`...;
   - выполняет `executeUpdate()`;
   - получает новый `id` через `getGeneratedKeys()`.
6. **PostgreSQL** проверяет ограничения (FOREIGN KEY, CHECK) и сохраняет строку.
7. Результат возвращается обратно: Repository → Service → UI, и `TablePrinter.printOrderDetails` печатает созданный заказ.
8. `BaseMenu.run` снова показывает подменю заказов.

Если на любом шаге возникла ошибка, исключение «всплывает» до `BaseMenu.run`, там перехватывается,
печатается «Ошибка: ...», и меню показывается снова. Программа не падает.

## 5. Файл за файлом

### Корень проекта

| Файл | Назначение |
|------|-----------|
| `pom.xml` | «паспорт» проекта для Maven: версия Java (17), библиотеки (драйвер PostgreSQL, Apache POI для Excel, log4j), плагины сборки |
| `db.properties` | адрес базы, логин, пароль |
| `sql/autoparts.sql` | создание таблиц и тестовые данные |
| `mvnw.cmd` / `mvnw` | Maven Wrapper — сам скачивает Maven, устанавливать его не нужно |

**Что такое Maven.** Программа для сборки Java-проектов. Она читает `pom.xml`, скачивает нужные библиотеки
из интернета, компилирует код и собирает jar-файл. Без Maven пришлось бы вручную искать и подключать
драйвер PostgreSQL и библиотеку для Excel.

### `Main.java` — точка входа

Java начинает выполнение с метода `public static void main(String[] args)`. Он:

1. создаёт `DatabaseManager` и проверяет подключение (если базы нет — понятное сообщение и выход);
2. создаёт репозитории, передавая им `DatabaseManager`;
3. создаёт сервисы, передавая им репозитории;
4. создаёт главное меню, передавая ему сервисы и список экспортёров;
5. запускает меню.

Такой приём (объект получает нужные ему объекты через конструктор, а не создаёт их сам) называется
**внедрением зависимостей**. Логики в `Main` нет, по заданию так и нужно.

### Пакет `model`

**`Customer`** — клиент. Поля: `id`, `fullName`, `phone`, `email`, `city`, `registeredAt`.
Два конструктора: для нового клиента (id ещё нет, его выдаст база) и для клиента, прочитанного из базы.

**`Order`** — заказ. Поля: `id`, `customerId` (ссылка на клиента), `customerName` (для удобного вывода, берётся через JOIN),
`partName`, `partNumber` (артикул), `carBrand`, `category`, `quantity`, `unitPrice`, `status`, `createdAt`.
Метод `getTotal()` вычисляет сумму = цена × количество. Сумма не хранится в базе, а считается, поэтому не может «разойтись» с ценой.

**`OrderStatus`** (enum) — статус заказа: `NEW`, `CONFIRMED`, `SHIPPED`, `DELIVERED`, `CANCELLED`.
У каждой константы есть русское название (`getTitle()`). Метод `getAllowedNext()` возвращает, в какие статусы можно перейти:
это бизнес-правило, записанное прямо в enum.

**`PartCategory`** (enum) — категория запчасти: `ENGINE` (Двигатель), `BRAKES` (Тормоза), `SUSPENSION` (Подвеска),
`ELECTRICAL` (Электрика), `FILTERS` (Фильтры), `BODY` (Кузов).

### Пакет `exception`

```
RuntimeException (стандартный класс Java)
   └── AppException                 — наше базовое исключение
         ├── EntityNotFoundException — запись с таким ID не найдена
         ├── BusinessException       — нарушено бизнес-правило / неверные данные
         └── DatabaseException       — ошибка подключения или SQL
```

Все наши исключения наследуются от `AppException`, поэтому их можно перехватить одним `catch`.
Наследование от `RuntimeException` делает их **непроверяемыми**: не нужно писать `throws` в каждом методе.

### Пакет `util`

**`DatabaseManager`** — читает `db.properties` и выдаёт соединения с базой (`getConnection()`).
`checkConnection()` вызывается при старте. Статический метод `translate(SQLException, ...)` превращает
технические ошибки базы в понятные: код `23505` означает «нарушен UNIQUE», `23503` — «нарушен FOREIGN KEY»,
`23514` — «нарушен CHECK», коды на `08` — «нет соединения».

**`DataExporter`** — интерфейс экспорта: методы `getFormatName()` и `export(...)`.
**`ExcelExporter`** — реализация для `.xlsx` (библиотека Apache POI): два листа «Заказы» и «Клиенты», жирные заголовки,
денежный формат, автоширина столбцов.
**`CsvExporter`** — реализация для `.csv`: текстовый файл, столбцы разделены `;`.

### Пакет `repository`

**`CrudRepository<T>`** — интерфейс с пятью методами: `save`, `findAll`, `findById`, `update`, `deleteById`.
`<T>` значит «для любого типа»: `CrudRepository<Customer>` работает с клиентами, `CrudRepository<Order>` — с заказами.

**`CustomerRepository`** и **`OrderRepository`** реализуют этот интерфейс (`implements CrudRepository<...>`).
Все SQL-запросы — константы в начале класса. Метод `mapRow(ResultSet)` превращает строку результата SELECT в объект.
`OrderRepository` дополнительно умеет искать (`searchByPartName` и др.) и считать заказы клиента (`countByCustomerId`).

### Пакет `service`

**`CustomerService`** — создание, изменение, удаление клиентов с проверками (формат телефона и email, запрет удалять клиента с заказами).

**`OrderService`** — всё про заказы: CRUD, смена статуса, поиск (передаёт в репозиторий), фильтрация и сортировка (Stream API).

**`OrderSort`** (enum) — способы сортировки. Каждая константа хранит название и `Comparator` (правило сравнения двух заказов).

**`StatisticsService`** — считает показатели для пункта «Статистика».

### Пакет `ui`

**`ConsoleInput`** — чтение с клавиатуры с проверкой. `readId` повторяет вопрос, пока не введут число.
`readOrKeep` при пустом вводе (Enter) оставляет старое значение, это нужно при редактировании.
`choose` выводит нумерованный список (статусы, категории, форматы) и возвращает выбранный элемент.

**`TablePrinter`** — печать таблиц клиентов и заказов в консоль.

**`BaseMenu`** — абстрактный класс, общий для всех меню. Метод `run()` — бесконечный цикл: показать пункты → прочитать номер →
`0` выход → иначе `handle(номер)` внутри `try/catch`. Абстрактные методы `getTitle()`, `getOptions()`, `handle()`
каждое меню реализует по-своему.

**`MainMenu`**, **`CustomerMenu`**, **`OrderMenu`**, **`SearchMenu`**, **`FilterMenu`**, **`SortMenu`** — наследники `BaseMenu`.

## 6. База данных

Схема: [er-diagram.png](er-diagram.png). Скрипт: [`sql/autoparts.sql`](../sql/autoparts.sql).

### Таблицы

**customers**: `id`, `full_name`, `phone`, `email`, `city`, `registered_at`.
**orders**: `id`, `customer_id`, `part_name`, `part_number`, `car_brand`, `category`, `quantity`, `unit_price`, `status`, `created_at`.

### Связь

`orders.customer_id → customers.id` — **один ко многим** (у клиента много заказов, у заказа один клиент).

### Ограничения

| Ограничение | Что делает | Пример в проекте |
|-------------|-----------|------------------|
| `PRIMARY KEY` | уникальный идентификатор строки, не бывает пустым | `id SERIAL PRIMARY KEY` — номер выдаётся автоматически (1, 2, 3...) |
| `FOREIGN KEY` | значение должно существовать в другой таблице | `customer_id` должен быть среди `customers.id` |
| `ON DELETE RESTRICT` | запрещает удалить «родителя», пока есть «дети» | нельзя удалить клиента с заказами |
| `NOT NULL` | поле обязательно | все поля |
| `UNIQUE` | значение не повторяется | телефон и email клиента |
| `CHECK` | допустимые значения | `quantity BETWEEN 1 AND 100`, `unit_price > 0`, `status IN ('NEW', ...)` |

**Как enum хранится в базе.** В столбце `status` лежит текст `'NEW'`, `'DELIVERED'`... Java превращает текст в enum
через `OrderStatus.valueOf("NEW")`, а enum в текст — через `status.name()`. `CHECK` в базе не даст записать другое значение.

**Почему ID может «перескочить».** Если вставка не удалась (например, дубликат телефона), счётчик `SERIAL` уже увеличился,
и следующий клиент получит номер через один. Это нормально: ID должен быть уникальным, а не идти подряд.

**Проверки и в Java, и в базе.** Сервис проверяет данные заранее, чтобы показать понятное сообщение.
Ограничения базы — последняя линия защиты, даже если данные попадут туда в обход программы (например, через psql).

## 7. JDBC

**JDBC** (Java Database Connectivity) — стандартный набор классов Java для работы с базами данных.
Код JDBC одинаков для любой базы, а конкретную базу поддерживает **драйвер** (у нас `org.postgresql:postgresql` в `pom.xml`).

### Основные объекты

| Объект | Что это | Где в коде |
|--------|---------|-----------|
| `DriverManager` | выдаёт соединение по адресу, логину и паролю | `DatabaseManager.getConnection()` |
| `Connection` | открытое соединение с базой | в каждом методе репозитория |
| `PreparedStatement` | подготовленный SQL-запрос с параметрами `?` | `connection.prepareStatement(SQL)` |
| `ResultSet` | результат SELECT, который читается построчно | `rs.next()`, `rs.getString("part_name")` |
| `SQLException` | ошибка при работе с базой | перехватывается в каждом методе репозитория |

### Типичный метод репозитория

```java
public Optional<Customer> findById(int id) {
    try (Connection connection = db.getConnection();                          // 1. открыть соединение
         PreparedStatement statement = connection.prepareStatement(SELECT_BY_ID)) { // 2. подготовить запрос
        statement.setInt(1, id);                                              // 3. подставить значение вместо ?
        try (ResultSet rs = statement.executeQuery()) {                       // 4. выполнить
            return rs.next() ? Optional.of(mapRow(rs)) : Optional.empty();    // 5. прочитать результат
        }
    } catch (SQLException e) {
        throw handle(e, "поиск клиента по ID");                               // 6. ошибку превратить в нашу
    }
}
```

- `executeQuery()` — для SELECT (возвращает `ResultSet`);
- `executeUpdate()` — для INSERT, UPDATE, DELETE (возвращает число изменённых строк).

### try-with-resources

`try (Connection c = ...; PreparedStatement s = ...) { ... }` — всё, что открыто в скобках, **закрывается автоматически**
при выходе из блока, даже если произошла ошибка. Без этого незакрытые соединения копились бы, и база перестала бы отвечать.

### Statement и PreparedStatement

**Неправильно (Statement + склейка строк):**

```java
String sql = "SELECT * FROM customers WHERE email = '" + email + "'";
statement.executeQuery(sql);
```

Если пользователь введёт `' OR '1'='1`, запрос станет таким:
`SELECT * FROM customers WHERE email = '' OR '1'='1'`. Условие всегда истинно, и вернутся все клиенты.
Это **SQL-инъекция**: пользователь меняет смысл запроса. Ввод `'; DROP TABLE customers; --` мог бы удалить таблицу.

**Правильно (PreparedStatement + параметры):**

```java
String sql = "SELECT * FROM customers WHERE email = ?";
PreparedStatement statement = connection.prepareStatement(sql);
statement.setString(1, email);
```

Запрос отправляется в базу отдельно от данных. Значение параметра всегда считается **просто значением**, а не частью SQL,
поэтому инъекция невозможна. Заодно не нужно думать о кавычках в тексте, и база может переиспользовать план запроса.

**В проекте все запросы параметризованы.** Даже в поиске `"%" + text + "%"` склеивается значение параметра, а не текст SQL:
запрос остаётся `... LIKE LOWER(?)`.

## 8. Бизнес-правила

| Правило | Где проверяется |
|---------|----------------|
| Заказ можно создать только для существующего клиента | `OrderService.ensureCustomerExists` + FOREIGN KEY |
| Количество от 1 до 100, цена больше 0, поля не пустые | `OrderService.validate` + CHECK |
| Статус меняется только по схеме Новый → Подтверждён → Отправлен → Доставлен (отменить можно новый или подтверждённый) | `OrderStatus.getAllowedNext` / `canChangeTo`, `OrderService.changeStatus` |
| Доставленный и отменённый заказ изменить нельзя (статус окончательный) | там же |
| Редактировать состав заказа можно только в статусе «Новый» | `OrderService.update` |
| Удалять можно только новые или отменённые заказы | `OrderService.delete` |
| Нельзя удалить клиента, у которого есть заказы | `CustomerService.delete` + `ON DELETE RESTRICT` |
| Телефон: 10–15 цифр, email — формат `x@y.z` | `CustomerService.validate` (регулярные выражения) |
| Телефон и email клиента уникальны | `UNIQUE` в базе → `BusinessException` в `CustomerRepository.handle` |

## 9. Поиск, фильтрация, сортировка

### Поиск (4 способа) — на стороне базы, через SQL

По названию запчасти, артикулу, марке автомобиля, ФИО клиента. Ищется **часть текста без учёта регистра**:

```sql
WHERE LOWER(o.part_name) LIKE LOWER(?)      -- параметр: '%фильтр%'
```

`%` означает «любые символы», поэтому `%фильтр%` найдёт «Масляный фильтр», «Воздушный фильтр», «Салонный фильтр».

### Фильтрация (5 фильтров) — в Java, через Stream API

По статусу, категории, клиенту, диапазону суммы, диапазону дат.

```java
return getAll().stream()                                  // превратить список в поток
        .filter(order -> order.getStatus() == status)     // оставить только подходящие
        .toList();                                        // собрать обратно в список
```

### Сортировка (4 способа) — в Java, через Stream API и Comparator

```java
return getAll().stream()
        .sorted(sort.getComparator())
        .toList();
```

Компараторы описаны в enum `OrderSort`:
`Comparator.comparing(Order::getCreatedAt).reversed()` — по дате, сначала новые;
`Comparator.comparing(Order::getTotal).reversed()` — по сумме, сначала дорогие и т. д.

**Почему поиск в SQL, а фильтры в Java?** Задание рекомендует показать оба подхода. Для большой базы выгоднее фильтровать
в SQL (по сети передаётся меньше данных), а для небольших объёмов Stream API проще и нагляднее.

## 10. Статистика и экспорт

### Статистика (`StatisticsService`)

Показатели: всего клиентов (SQL `COUNT(*)`), всего заказов, активных, по каждому статусу, выручка по доставленным,
средняя сумма заказа, самая популярная категория, лучший клиент. Считаются через Stream API:

- `Collectors.groupingBy(Order::getStatus, ..., Collectors.counting())` — сгруппировать по статусу и посчитать → `Map<OrderStatus, Long>`;
- `.map(Order::getTotal).reduce(BigDecimal.ZERO, BigDecimal::add)` — сложить суммы.

Результат — `LinkedHashMap`: в отличие от `HashMap`, он помнит порядок добавления, поэтому показатели выводятся в задуманном порядке.
`EnumMap` — `Map`, где ключи — константы enum; работает быстро и хранит их в порядке объявления.

### Экспорт

Пункт 7: выбрать формат → файл сохраняется в папку `exports/` (имя содержит дату и время, файлы не перезаписываются).

- **Excel (.xlsx)** — `ExcelExporter` на библиотеке Apache POI: `XSSFWorkbook` (книга) → `Sheet` (лист) → `Row` (строка) → `Cell` (ячейка).
- **CSV** — `CsvExporter`: обычный текстовый файл. В начале стоит символ BOM, чтобы Excel правильно показал русские буквы.

Данные для экспорта берутся из PostgreSQL через сервисы.

## 11. Обработка ошибок

| Ситуация | Что происходит | Где |
|----------|---------------|-----|
| Ввели текст вместо числа (`abc`) | «Ошибка: ID должен быть целым числом.», вопрос повторяется | `ConsoleInput.readInt` ловит `NumberFormatException` |
| Неверная дата (`31.13.2026`) | сообщение о формате, вопрос повторяется | `ConsoleInput.readDate` ловит `DateTimeParseException` |
| Нет пункта меню (`9`) | «Ошибка: такого пункта меню нет.» | `BaseMenu.run` |
| Нет записи с таким ID | «Ошибка: Заказ с ID 99 не найден.» | `EntityNotFoundException` из сервиса |
| Нарушено бизнес-правило | «Ошибка: Удалять можно только новые или отменённые заказы...» | `BusinessException` из сервиса |
| Дубликат телефона/email | «Ошибка: Клиент с таким телефоном или email уже существует.» | `SQLException` с кодом 23505 → `BusinessException` |
| База недоступна при запуске | сообщение с подсказкой, программа корректно завершается | `Main` ловит `DatabaseException` |
| База пропала во время работы | «Ошибка: проблема с базой данных...», меню продолжает работать | `DatabaseException` → `BaseMenu.run` |
| Ошибка SQL-запроса | «Ошибка SQL-запроса (...)» | `DatabaseManager.translate` |
| Не удалось записать файл экспорта | «Ошибка: не удалось сохранить файл...» | `MainMenu.exportData` ловит `IOException` |

Главная идея: все ошибки превращаются в наши исключения и перехватываются в **одном месте** — `BaseMenu.run()`.
Поэтому после любой ошибки программа возвращается в меню.

## 13. Вопросы на защите и ответы

**Назначение основных классов.**
`Main` — точка входа, собирает объекты. `Customer`, `Order` — данные. `OrderStatus`, `PartCategory` — допустимые значения.
Репозитории — SQL. Сервисы — бизнес-логика. Меню — работа с пользователем. `DatabaseManager` — подключение. Экспортёры — выгрузка в файлы.

**Что такое инкапсуляция и где она применяется?**
Сокрытие внутреннего состояния объекта: поля `private`, доступ только через методы. Класс сам контролирует свои данные.
Например, у `Order` нет поля «сумма», которое можно испортить: сумма всегда вычисляется `getTotal()`.
У `Customer` нет сеттера для даты регистрации, поэтому её нельзя изменить после создания.

**Зачем нужны интерфейсы?**
Интерфейс — это договор: какие методы должны быть у класса, без их реализации. Код, который работает через интерфейс,
не зависит от конкретного класса. `MainMenu` вызывает `exporter.export(...)` и не знает, Excel это или CSV.
Чтобы добавить экспорт в PDF, достаточно написать новый класс `implements DataExporter`, а меню менять не нужно.

**Зачем enum?**
Когда значение может быть только одним из фиксированного списка (статус, категория). Компилятор не даст написать
несуществующий статус, а в enum можно хранить данные (русское название) и логику (разрешённые переходы).
Со строками `"NEW"` легко опечататься, и ошибка обнаружится только во время работы.

**Что такое полиморфизм и где он у вас?**
Один и тот же вызов работает по-разному в зависимости от реального класса объекта.
`BaseMenu.run()` вызывает `handle(choice)`, но выполняется `handle` того меню, которое реально запущено: `OrderMenu`, `SearchMenu`...
Аналогично `exporter.export(...)` для `ExcelExporter` и `CsvExporter`. Это достигается через наследование
(`extends`) / реализацию интерфейса (`implements`) и переопределение методов (`@Override`).

**Какие коллекции используются?**
`List` / `ArrayList` — упорядоченные списки клиентов и заказов. `Map` — пары «ключ → значение»:
`LinkedHashMap` (сохраняет порядок) для статистики, `EnumMap` для подсчёта по статусам, `HashMap` внутри `groupingBy`.
`List.of(...)` — неизменяемый список (пункты меню, разрешённые статусы).

**Как устроена обработка исключений?**
Раздел 11. Своя иерархия от `AppException`; технические ошибки (`SQLException`, `NumberFormatException`) перехватываются
и превращаются в понятные сообщения; всё собирается в `try/catch` в `BaseMenu.run()`, поэтому программа не падает.

**Как работает JDBC?** Раздел 7: `DriverManager` → `Connection` → `PreparedStatement` → `executeQuery/executeUpdate` → `ResultSet`, всё в try-with-resources.

**Отличие Statement от PreparedStatement?**
`Statement` выполняет готовую строку SQL; если склеить её с вводом пользователя, возможна SQL-инъекция.
`PreparedStatement` компилирует запрос с `?` заранее, значения передаются отдельно и не могут изменить смысл запроса.
Плюс: не нужно экранировать кавычки, база может переиспользовать план запроса.

**Связи между таблицами?**
Один ко многим: `orders.customer_id` — внешний ключ на `customers.id`. `ON DELETE RESTRICT` запрещает удалить клиента с заказами.
В запросах связь используется через `JOIN customers c ON c.id = o.customer_id`, чтобы получить имя клиента.

**Основные бизнес-правила?** Раздел 8.

**Как создаются, изменяются, удаляются записи?**
Меню собирает данные → сервис проверяет → репозиторий выполняет `INSERT` / `UPDATE` / `DELETE` через `PreparedStatement`.
При создании `id` генерирует база (`SERIAL`), программа получает его через `getGeneratedKeys()`.
Перед удалением программа просит подтверждение (да/нет).

**Как работают поиск, фильтрация, сортировка?** Раздел 9.

**Как работает экспорт?** Раздел 10.

### Вопросы, которые тоже могут задать

- **Что такое `Optional`?** Контейнер «значение или пусто». `findById` возвращает `Optional`, а сервис делает
  `.orElseThrow(() -> new EntityNotFoundException(...))`, то есть «дай значение, а если его нет, выбрось исключение».
  Так не нужно возвращать `null` и ловить `NullPointerException`.
- **Что такое `@Override`?** Пометка «этот метод переопределяет метод родителя / интерфейса». Если ошибиться в имени,
  компилятор сообщит об ошибке.
- **Чем абстрактный класс отличается от интерфейса?** Абстрактный класс (`BaseMenu`) может содержать поля и готовые методы
  (`run()`), а наследоваться можно только от одного класса. Интерфейс описывает только договор, а реализовать класс может несколько интерфейсов.
- **Проверяемые и непроверяемые исключения?** Проверяемые (`IOException`, `SQLException`) компилятор заставляет обработать
  или объявить в `throws`. Непроверяемые (`RuntimeException` и наследники) — не заставляет. Наши исключения непроверяемые.
- **Зачем generics `<T>`?** Чтобы один интерфейс `CrudRepository<T>` подходил для разных типов и компилятор проверял типы.
- **Зачем `static` в `TablePrinter`?** У класса нет своего состояния, это просто набор функций печати, поэтому создавать объект не нужно.
- **Что будет, если выключить PostgreSQL во время работы?** Следующее действие выведет «Ошибка: проблема с базой данных...», и меню продолжит работать.
- **Почему соединение открывается на каждый запрос?** Так проще и надёжнее для учебного проекта: соединение гарантированно закрывается.
  В реальных системах используют пул соединений (например, HikariCP).
