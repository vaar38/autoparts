## 1. Что изменилось по сравнению с КР №1

| Было в КР №1 | Стало в КР №2 |
|---|---|
| Консольное меню (`ui/*Menu.java`, `Main.java`) | Окно JavaFX: разметка в FXML, логика окон в контроллерах (`fx/controller`) |
| Настройки БД в `db.properties` в корне | `src/main/resources/database.properties` (как в методичке), читается из classpath |
| Java 17 | Java 21, JavaFX 21 (pom.xml по образцу методички) |
| Поиск SQL-запросом по одному выбранному полю | Поиск сразу по 4 полям + фильтры, применяются мгновенно (`OrderFilter`) |
| Экспорт в папку `exports/` | Путь выбирает пользователь через `FileChooser` |
| Ошибка — текст в консоли | Диалоговое окно, красная рамка у неверного поля |

Без изменений остались: таблицы `customers` и `orders`, скрипт `sql/autoparts.sql`, модели, репозитории (JDBC),
бизнес-правила (смена статусов, что можно менять и удалять).

## 2. Как запустить

1. PostgreSQL запущен, база `autoparts` создана скриптом `sql/autoparts.sql` (как в КР №1).
2. Скопировать `src/main/resources/database.properties.example` в `database.properties` (та же папка) и вписать свой пароль.
3. Из папки проекта: `.\run.cmd` — или `mvn javafx:run`, или `.\mvnw.cmd javafx:run` (если Maven не установлен).

Тесты: `mvn test`. Сборка: `mvn clean package`.

Что происходит при запуске: плагин `javafx-maven-plugin` компилирует проект и запускает класс
`ru.mirea.autoparts.fx.AutopartsApp`. JavaFX вызывает его метод `start(Stage)`. Там:
1) создаётся `DatabaseManager` и проверяется подключение (если базы нет — окно с ошибкой и выход);
2) создаётся `AppContext` — он собирает репозитории и сервисы;
3) `ViewLoader` загружает `MainView.fxml`, кладёт его в `Scene`, сцена ставится в окно (`Stage`) и окно показывается.

## 3. Docker и готовая система из архива

Готовая система преподавателя (backend на Spring Boot + PostgreSQL + веб-интерфейс + JavaFX-клиент)
запускается так:

1. Установить и запустить **Docker Desktop**, дождаться статуса *Running*.
2. Распаковать архив целиком, проверить, что в корне есть файл `.env`.
3. В корне архива: `docker compose --env-file .env -f backend/docker-compose.yml up -d --wait`
   (или `powershell -ExecutionPolicy Bypass -File .\backend\start-compose.ps1`).
4. Проверка: `docker compose --env-file .env -f backend/docker-compose.yml ps` — контейнер PostgreSQL в состоянии
   *healthy* (прошёл healthcheck), backend запущен; в браузере открываются `http://localhost:8080/` и
   `http://localhost:8080/actuator/health` (ответ `{"status":"UP"}`).
5. Войти в веб-интерфейс: `admin@example.org` / пароль из `.env`.
6. Только после этого: `cd javafx-client`, `mvn javafx:run`.
7. Остановка: `docker compose --env-file .env -f backend/docker-compose.yml down` (без `-v`, чтобы не удалить данные).

**Важная разница.** Клиент из архива ходит в базу через REST API (JavaFX → HTTP → Spring Boot → PostgreSQL).
Наше приложение подключается к своей базе КР №1 **напрямую через JDBC** (JavaFX → JDBC → PostgreSQL),
поэтому backend ему не нужен.

**Наша база в Docker (необязательно).** Если у участника нет локального PostgreSQL, в проекте есть `docker-compose.yml`:
скопировать `.env.example` в `.env`, задать пароль, выполнить `docker compose up -d --wait`.
Контейнер сам создаст базу и выполнит `sql/autoparts.sql`. Порт на компьютере — `55433`
(внутри контейнера PostgreSQL слушает обычный 5432), поэтому в `database.properties`:
`db.url=jdbc:postgresql://localhost:55433/autoparts`, `db.user=autoparts`.

## 4. Основы JavaFX: Stage, Scene, Node

- **Stage** — окно операционной системы (рамка, заголовок, кнопки свернуть/закрыть). Главное окно JavaFX создаёт сам
  и передаёт в `start(Stage stage)`. Диалоги — отдельные окна, у них свой Stage.
- **Scene** — содержимое окна. В окне в каждый момент одна сцена. К сцене подключается CSS:
  `scene.getStylesheets().add(...)`.
- **Node** — любой элемент внутри сцены: кнопка, таблица, метка, панель. Элементы образуют дерево (*scene graph*):
  `BorderPane` содержит `TabPane`, тот — вкладки, внутри вкладки — `TableView` и т.д.
- **Панели раскладки:** `BorderPane` (верх/центр/право/низ), `VBox`/`HBox` (столбик/строка), `GridPane` (сетка — формы),
  `FlowPane` (переносит элементы на новую строку — карточки статистики), `SplitPane` (две части с перетаскиваемой границей).
- **Поток JavaFX Application Thread.** Весь интерфейс меняется только в нём. Обработчики кнопок выполняются в нём же.
  Запросы к нашей локальной базе быстрые, поэтому выполняются там же — окно не «подвисает».

Код: [AutopartsApp.java](../src/main/java/ru/mirea/autoparts/fx/AutopartsApp.java).

## 5. FXML, контроллер, fx:id, обработчики

**FXML** — XML-файл с описанием интерфейса: какие элементы, как вложены, какие подписи. Зачем:
внешний вид отделён от Java-кода, его легко читать и менять, не трогая логику.
Файлы лежат в `src/main/resources/ru/mirea/autoparts/fx/view/`.

**Связь FXML и контроллера** (пример из `OrdersView.fxml` и `OrdersController.java`):

```xml
<BorderPane fx:controller="ru.mirea.autoparts.fx.controller.OrdersController" ...>
    <TextField fx:id="searchField" .../>
    <Button text="Удалить" onAction="#onDelete"/>
```

```java
public class OrdersController {
    @FXML private TextField searchField;   // FXMLLoader положит сюда TextField с fx:id="searchField"

    @FXML
    private void onDelete() { ... }        // вызывается при нажатии кнопки (onAction="#onDelete")

    @FXML
    private void initialize() { ... }      // вызывается один раз, когда все @FXML-поля уже заполнены
}
```

- `fx:controller` — какой класс обслуживает разметку. `FXMLLoader` создаёт его объект.
- `fx:id` — имя элемента; поле с таким же именем и аннотацией `@FXML` получает ссылку на элемент.
- `onAction="#метод"` — обработчик события: метод контроллера, который вызовется при нажатии.
- `@FXML` нужна, чтобы FXMLLoader мог заполнить даже `private`-поля и вызывать `private`-методы.
- `initialize()` — место для настройки, которую нельзя описать в FXML (столбцы таблицы, слушатели).

**Как контроллер получает сервисы.** В [ViewLoader](../src/main/java/ru/mirea/autoparts/fx/util/ViewLoader.java)
у FXMLLoader задана *фабрика контроллеров*: контроллер создаётся конструктором `new OrdersController(appContext)`,
поэтому сервисы доступны ему сразу.

**fx:include.** Главное окно (`MainView.fxml`) подключает три вкладки как отдельные файлы:
`<fx:include fx:id="ordersView" source="OrdersView.fxml"/>`. Контроллер вложенного файла FXMLLoader кладёт в поле
главного контроллера с именем `fx:id + "Controller"` — `ordersViewController`. Так `MainController` может обновить
вкладку при переключении или вызвать экспорт из меню.

## 6. Архитектура: слои и пакеты

```
ru.mirea.autoparts
├── fx/                  JavaFX
│   ├── AutopartsApp     точка входа (Application.start)
│   ├── Launcher         запуск из IDE кнопкой Run
│   ├── AppContext       создаёт и связывает объекты всех слоёв
│   ├── controller/      Controller — действия пользователя, работа с элементами окна
│   └── util/            общие помощники интерфейса: диалоги, загрузка FXML, столбцы таблиц, ошибки форм
├── service/             Service — бизнес-правила, проверки, поиск/фильтр, статистика
├── repository/          Repository/DAO — SQL-запросы через JDBC
├── model/               Модели: Customer, Order, OrderStatus, PartCategory
├── exception/           Свои исключения
└── util/                DatabaseManager (подключение), экспорт, форматы чисел и дат
resources/ru/mirea/autoparts/fx/
├── view/*.fxml          View — разметка окон
└── styles/app.css       оформление
```

| Слой | Что делает | Пример |
|---|---|---|
| View / FXML | Как выглядит окно | `OrdersView.fxml` |
| Controller | Принимает нажатия, читает поля, вызывает сервис, обновляет таблицу | `OrdersController.onDelete()` |
| Service | Правила: «удалять можно только новые и отменённые заказы» | `OrderService.delete()` |
| Repository / DAO | SQL: `DELETE FROM orders WHERE id = ?` | `OrderRepository.deleteById()` |
| Database | Хранение, `FOREIGN KEY`, `CHECK`, `UNIQUE` | `sql/autoparts.sql` |

**Путь действия «Удалить заказ»:** кнопка (FXML, `onAction="#onDelete"`) → `OrdersController.onDelete()` показывает
подтверждение → `OrderService.delete(id)` проверяет статус → `OrderRepository.deleteById(id)` выполняет SQL →
контроллер вызывает `refresh()` → `orders.setAll(...)` → таблица перерисовывается.

В контроллерах **нет SQL**, а в сервисах **нет JavaFX** — сервисы можно проверить тестами без окна (`src/test`).

## 7. TableView и ObservableList

**ObservableList** — список, который сообщает подписчикам о любом изменении (добавили, удалили, заменили элементы).
`TableView` подписывается на свой список `items` и сама перерисовывается. Поэтому после добавления/изменения/удаления
мы не трогаем строки таблицы вручную, а просто обновляем список:

```java
orders.setAll(orderService.getAll());   // свежие данные из БД -> таблица обновится сама
```

**Цепочка списков в `OrdersController`:**

```
orders  (ObservableList — все заказы из БД)
  └─ filteredOrders  (FilteredList — только подходящие под поиск и фильтры)
       └─ sortedOrders  (SortedList — в нужном порядке)  ->  ordersTable.setItems(sortedOrders)
```

Эти обёртки тоже наблюдаемые: изменилось условие фильтра или исходный список — пересчитываются автоматически.
Надпись «Показано заказов: 5 из 15» привязана к размерам списков через `Bindings` и тоже обновляется сама.

**Столбцы.** `cellValueFactory` говорит, *откуда* столбец берёт значение (`Order::getTotal`), `cellFactory` —
*как* его нарисовать («3 700,00»). Это вынесено в [TableColumns](../src/main/java/ru/mirea/autoparts/fx/util/TableColumns.java),
чтобы не повторять в каждом контроллере. Технические данные (`customer_id`) пользователю не показываются:
вместо них — ФИО клиента.

**Выбор строки:** `ordersTable.getSelectionModel().selectedItemProperty()` — слушатель обновляет панель
«Сведения о заказе» и включает/выключает кнопки «Изменить», «Сменить статус», «Удалить».

## 8. Поиск, фильтрация, сортировка

**Поиск** — одно поле, ищет без учёта регистра сразу в 4 полях: название запчасти, артикул, марка авто, ФИО клиента.
**Фильтры** — статус, категория, период дат создания заказа (с … по …), кнопка «За 30 дней».
Все условия собираются в объект [OrderFilter](../src/main/java/ru/mirea/autoparts/service/OrderFilter.java) (слой Service):

```java
OrderFilter filter = new OrderFilter(searchField.getText(), statusFilter.getValue(),
        categoryFilter.getValue(), dateFromPicker.getValue(), dateToPicker.getValue());
filteredOrders.setPredicate(filter::matches);   // таблица покажет только заказы, для которых matches == true
```

Фильтр применяется при каждом изменении поля (слушатели `textProperty`/`valueProperty`) — кнопка «Найти» не нужна.
Данные не перечитываются из БД при каждом нажатии клавиши: фильтруются уже загруженные заказы в памяти.
Если «дата с» позже «даты по», конструктор `OrderFilter` бросает `ValidationException`, и под фильтрами появляется
красное сообщение.

На вкладке «Клиенты» — поиск по ФИО/телефону/email и фильтр по городу (`CustomerService.matches`).

**Сортировка — два способа:**
1. Щелчок по заголовку любого столбца (по возрастанию → по убыванию → без сортировки); Shift+щелчок — по нескольким столбцам.
2. Список «Сортировка» с готовыми вариантами из enum [OrderSort](../src/main/java/ru/mirea/autoparts/service/OrderSort.java):
   по дате, по сумме, по ФИО клиента, по названию запчасти.

Как это работает: TableView сама строки не переставляет — она хранит `comparator` (правило сравнения по выбранным
столбцам). Строки переставляет `SortedList`, у которого компаратор привязан (`bind`) к выражению: «если выбраны
столбцы — компаратор таблицы, иначе — компаратор из списка `OrderSort`». Сортировка идёт по настоящим значениям
(числам, датам), а не по тексту на экране — поэтому «9 000» не окажется больше «12 500».

## 9. Формы, валидация и диалоговые окна

**Форма заказа** — `OrderDialog.fxml` + `OrderDialogController`, одна и для добавления, и для редактирования.
При редактировании поля заполняются текущими значениями (`fillForm`). Корень разметки — `DialogPane`; контроллер
вставляет его в `Dialog` и добавляет кнопки «Сохранить»/«Отмена».

**Проверка до сохранения.** На кнопку «Сохранить» повешен *фильтр события*: если данные неверны, вызывается
`event.consume()` — окно не закрывается, введённое не теряется.

Что проверяется и где:

| Проверка | Где |
|---|---|
| Пустые обязательные поля | `Validation.requireText` (вызывают сервисы) |
| Длина строк = размер VARCHAR в таблице (100, 30, 50…) | `Validation.requireText(..., maxLength)` |
| Число, а не текст; диапазон 1–100 шт.; цена > 0, не больше NUMERIC(10,2), не больше 2 знаков копеек | `Validation.parseInt/parseMoney`, `OrderService.validate` |
| Формат телефона, email, артикула | `CustomerService.validate`, `OrderService.validate` |
| Даты: регистрация не в будущем и не раньше 2000 г.; период «с» ≤ «по» | `CustomerService.validate`, `OrderFilter`, `StatisticsService` |
| Уникальность телефона и email | `CustomerRepository.existsByPhone/existsByEmail` (+ `UNIQUE` в БД) |
| Связанный клиент выбран и существует | `OrderService.validate` (+ `FOREIGN KEY` в БД) |
| Бизнес-правила: менять только «Новые», удалять только «Новые»/«Отменённые», переходы статусов, нельзя удалить клиента с заказами | `OrderService`, `OrderStatus`, `CustomerService.delete` |

**Как пользователь видит ошибку.** Сервис бросает `ValidationException(поле, сообщение)`. Форма через
[FormErrors](../src/main/java/ru/mirea/autoparts/fx/util/FormErrors.java) находит элемент по имени поля,
обводит его красной рамкой (CSS-класс `field-error`), ставит в него курсор и показывает сообщение
вроде «Поле «Количество» должно быть от 1 до 100». Рамка исчезает, как только поле начали исправлять.

**Диалоговые окна** — в [Dialogs](../src/main/java/ru/mirea/autoparts/fx/util/Dialogs.java):
`error` (ошибка), `info` (успешный экспорт — важная операция с файлом), `confirm` (подтверждение удаления, по умолчанию
выделена «Отмена», чтобы случайный Enter ничего не удалил), `choose` (выбор нового статуса — предлагаются только
разрешённые переходы).

## 10. Связанные сущности

Связь в БД: `orders.customer_id → customers.id` (один клиент — много заказов).

- В форме заказа клиент **выбирается из списка** (`ComboBox<Customer>`), ID вручную не вводится.
  В списке клиент выглядит как «ФИО (телефон)» — это `Customer.toString()`.
- Панель «Сведения о заказе» справа показывает и данные клиента (телефон, email, город).
- Вкладка «Клиенты»: при выборе клиента внизу появляются **его заказы** и их общая сумма
  (`OrderService.getByCustomer` → SQL `WHERE o.customer_id = ?`).
- Удалить клиента с заказами нельзя: это проверяет `CustomerService.delete`, а в БД стоит `ON DELETE RESTRICT`.

## 11. Обработка исключений

Иерархия (из КР №1, плюс одно новое):

```
RuntimeException
└─ AppException                 — все ошибки нашего приложения
   ├─ BusinessException         — неверные данные или нарушено правило
   │  └─ ValidationException    — НОВОЕ: неверно заполнено конкретное поле (хранит имя поля)
   ├─ DatabaseException         — нет связи с БД, ошибка SQL
   └─ EntityNotFoundException   — запись не найдена
```

- Репозиторий ловит `SQLException` и превращает её в понятное исключение (`DatabaseManager.translate`).
- Обработчики кнопок запускают действия через [UiActions.run](../src/main/java/ru/mirea/autoparts/fx/util/UiActions.java):
  `BusinessException` → окно с текстом ошибки; `DatabaseException` → окно + запись в журнал;
  любая другая ошибка → окно «непредвиденная ошибка», а stack trace — только в журнал (SLF4J), не пользователю.
- Пустых `catch` нет: каждый `catch` либо показывает сообщение, либо пишет в журнал, либо и то и другое.
- Для ошибок, которые всё-таки «вылетели» мимо обработчиков, в `AutopartsApp` задан `UncaughtExceptionHandler`.
- Нет базы при запуске → окно «Нет подключения к базе данных» с подсказкой, что проверить, и выход.

## 12. Статистика

Вкладка «Статистика», расчёт — [StatisticsService](../src/main/java/ru/mirea/autoparts/service/StatisticsService.java)
(Stream API по списку заказов из БД):

| Показатель | Как считается |
|---|---|
| Всего клиентов | `SELECT COUNT(*)` в репозитории |
| Всего заказов | размер списка |
| Активных заказов | `filter(status.isActive())` — Новый, Подтверждён, Отправлен |
| Доля отменённых | отменённые / все × 100 % |
| Выручка | сумма `getTotal()` доставленных заказов |
| Средняя / минимальная / максимальная сумма заказа | по неотменённым заказам: `reduce`, `min`, `max` |
| Самая популярная категория | `groupingBy(категория, summingInt(количество))`, затем максимум |
| Лучший клиент | `groupingBy(клиент, сумма заказов)`, затем максимум |
| За выбранный период | число заказов, неотменённых, их сумма и средний чек между двумя датами |

Диаграммы: круговая (`PieChart`) — сумма по категориям, столбчатая (`BarChart`) — число заказов по статусам.
Статистика пересчитывается при каждом открытии вкладки.

## 13. Экспорт

Кнопка «Экспорт…» (или меню Файл → Экспорт, Ctrl+E). Выгружается **текущий набор** — ровно те заказы, что видны
в таблице, с учётом поиска, фильтров и сортировки (`new ArrayList<>(sortedOrders)`).

1. `FileChooser` — системное окно «Сохранить как». В нём два типа файла: Excel (.xlsx) и CSV (.csv).
   Путь выбирает пользователь, в коде путей к папкам нет.
2. По выбранному типу берётся нужный экспортёр — объект интерфейса `DataExporter` (`ExcelExporter` или `CsvExporter`;
   это полиморфизм). Если пользователь не дописал расширение, оно добавляется.
3. Excel — через библиотеку Apache POI, два листа: «Заказы» и «Клиенты». CSV — текст с разделителем `;` и BOM,
   чтобы Excel правильно показал русские буквы.
4. Если файл занят (открыт в Excel) — понятное сообщение об ошибке.

## 14. CSS

Файл [app.css](../src/main/resources/ru/mirea/autoparts/fx/styles/app.css) подключается к главной сцене
и ко всем диалогам. Свойства JavaFX CSS начинаются с `-fx-`. Классы элементам задаются в FXML
(`styleClass="primary-button"`) или из кода (`getStyleClass().add("status-new")`).

Оформлены: кнопки (основная синяя, «опасная» красная, ссылки), таблицы (заголовки, чередование строк, выделение,
цвет статуса), формы (поля, рамка в фокусе), заголовки и панели, состояние ошибки (`.field-error`, `.error-label`),
карточки статистики. Цвета вынесены в переменные в `.root`.

Изменение размера окна: столбцы таблиц растягиваются (`CONSTRAINED_RESIZE_POLICY`), панель фильтров переносит
элементы на новую строку (`FlowPane`), у окна задан минимальный размер.

## 16. Вопросы на защите и ответы

**Что такое Stage, Scene, Node?** Stage — окно, Scene — его содержимое, Node — любой элемент в сцене. Дерево узлов
называется scene graph. См. раздел 4.

**Зачем FXML?** Чтобы описать интерфейс отдельно от логики: разметку легче читать и менять, контроллер не
загромождается созданием кнопок и панелей.

**Как FXML связан с контроллером?** Атрибут `fx:controller` — класс контроллера; `fx:id` — имя поля с `@FXML`;
`onAction="#метод"` — обработчик. Всё связывает `FXMLLoader` при загрузке. После этого он вызывает `initialize()`.

**Как обновляются данные в TableView?** Таблица показывает `ObservableList`. После любой операции мы перечитываем
данные из БД и делаем `orders.setAll(...)` — список сообщает таблице об изменении, и она перерисовывается.

**Зачем ObservableList?** Обычный `ArrayList` не сообщает об изменениях — таблицу пришлось бы обновлять вручную.
ObservableList сам уведомляет таблицу. На нём же построены `FilteredList` (фильтр) и `SortedList` (сортировка).

**Где бизнес-логика?** В пакете `service`: `OrderService` (правила заказов), `CustomerService`, `OrderFilter`,
`StatisticsService`, `Validation`, а правила переходов статусов — в `OrderStatus`.

**Где работа с данными?** В пакете `repository` (DAO): `CustomerRepository`, `OrderRepository` — SQL с `PreparedStatement`.
Подключение — `DatabaseManager`, настройки — `database.properties`.

**Почему SQL не в обработчиках кнопок?** Так требует разделение на слои: контроллер отвечает за окно, репозиторий —
за базу. Если поменяется база или запрос, контроллер трогать не придётся; сервисы можно тестировать без окна.

**Как обрабатываются исключения?** Раздел 11: свои исключения, `UiActions.run` → понятное окно, подробности в журнал.

**Как проверяются данные?** Раздел 9: сначала числа разбираются из текста (`Validation.parseInt/parseMoney`), потом
сервис проверяет все правила, и только потом репозиторий пишет в БД. Ограничения в самой БД — вторая линия защиты.

**Как реализован поиск и фильтрация?** Раздел 8: `OrderFilter.matches` + `FilteredList.setPredicate`.

**Как рассчитывается статистика?** Раздел 12: Stream API — `filter`, `map`, `reduce`, `groupingBy`, `max`.

**Как выполняется экспорт?** Раздел 13: `FileChooser` → выбор `DataExporter` по типу файла → Apache POI / CSV.

**Почему пароль не в коде?** Он в `src/main/resources/database.properties`, который указан в `.gitignore`.
В git лежит только образец `database.properties.example`.

**Как попадает database.properties в программу?** Плагин `maven-resources-plugin` копирует `src/main/resources`
в `target/classes`; `DatabaseManager` читает файл из classpath через `getResourceAsStream`.

**Что такое `@FXML`?** Аннотация, разрешающая FXMLLoader заполнять приватные поля и вызывать приватные методы.

**Что такое `Platform.exit()`?** Корректное завершение JavaFX-приложения (меню Файл → Выход).

**Что такое record (`OrderFilter`)?** Короткая запись неизменяемого класса с данными: Java сама создаёт конструктор,
геттеры, `equals`, `toString`. В «компактном конструкторе» мы проверяем, что период дат корректный.

**Зачем `Launcher`?** Если запускать наследника `Application` напрямую из IDE без модулей JavaFX, Java пишет
«JavaFX runtime components are missing». Отдельный класс с `main` обходит эту проверку. Основной запуск — `mvn javafx:run`.

**Чем наш клиент отличается от javafx-client из архива?** Тот работает через REST API backend-а,
наш — напрямую через JDBC к базе КР №1.

## 17. Сценарий демонстрации

1. Показать, что PostgreSQL запущен, и `.\run.cmd` — открывается окно; в шапке адрес базы.
2. **Таблица заказов**: щёлкнуть строку — справа сведения о заказе и о клиенте.
3. **Поиск**: ввести «bmw», затем «иванов» — таблица фильтруется на лету, внизу «Показано N из 15».
4. **Фильтры**: статус «Новый», категория «Тормоза», период «За 30 дней»; «Сбросить».
   Показать ошибку: дата «с» позже даты «по».
5. **Сортировка**: список «По сумме заказа», затем щелчок по заголовку «Клиент», Shift+щелчок по «Дата».
6. **Добавление**: «Новый заказ» → нажать «Добавить» с пустыми полями (ошибка), количество 500 (ошибка диапазона),
   цена «abc» (ошибка числа) → заполнить правильно → заказ появился в таблице и выделен.
7. **Редактирование**: двойной щелчок по новому заказу → форма с текущими значениями → изменить → сохранить.
   Попробовать изменить доставленный заказ → сообщение о бизнес-правиле.
8. **Смена статуса**: «Сменить статус» → предлагаются только разрешённые статусы.
9. **Удаление**: «Удалить» → подтверждение → заказ исчез. Попробовать удалить отправленный → правило не даёт.
10. **Клиенты**: выбрать клиента — внизу его заказы; добавить клиента с уже существующим телефоном — ошибка
    уникальности; удалить клиента с заказами — запрет.
11. **Статистика**: карточки показателей, расчёт за период, диаграммы.
12. **Экспорт**: отфильтровать, «Экспорт…» → выбрать папку и тип → открыть файл в Excel.
